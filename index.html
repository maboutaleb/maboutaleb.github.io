Try the Source Trust Pipeline

A working miniature of the Source Trust Pipeline — the three engines that turn three independent revenue sources per property-month into one certified trust score. Every formula and threshold below is ported directly from the production code (source_trust_monthly_pipeline_v4.py): the symmetric %-difference and suspected-source logic, the trailing-baseline z-score that separates a fast spike from a slow drift, and the 35/30/20/15 weighted score with its rating and status labels.

Note on data: the real pipeline runs on internal, non-public revenue data. Every number you enter or see below is illustrative — the logic is exact, the values are yours to play with.

source-trust · pipeline v4

Stage 1 — reconcile one property-month. Three systems each report the same month's revenue. The pipeline compares them pairwise with a scale-free symmetric %-difference, flags the month as aligned only if the largest gap is within tolerance, and — when exactly two of three agree — names the odd source out.

diff = 2×|a−b| / (|a|+|b|)  ·  aligned = max(pairwise diff) ≤ tolerance  ·  suspected source = the one not in the only within-tolerance pair

Stage 2 — is this month's gap actually abnormal? A 5% gap means little on its own — some properties are just noisier. So each month's %-difference is turned into a z-score against that property's own trailing 12-month baseline. A single extreme month (z ≥ 6) is a fast spike; three elevated months in a row (z ≥ 2 each) is a slow drift. Drag the three most recent months, or load a preset.

z = (diff − baseline_mean) / baseline_std  ·  fast_spike = diff > 5% and z ≥ 6  ·  slow_drift = 3 consecutive months with diff > 5% and z ≥ 2

Stage 3 — roll it up into one certified score. Per property, four components combine into a single 0–100 trust score, which maps to a plain-English rating and a current status. Revenue alignment carries the most weight; stability (freedom from drift) the least. Toggle an active or historical issue to see how status is gated independently of the raw score.

score = 0.35·revenue + 0.30·rooms + 0.20·completeness + 0.15·stability  ·  rating: ≥95 EXCELLENT · ≥85 GOOD · ≥70 REVIEW · ≥50 MATERIAL · else SEVERE

What the pipeline emits, and why it's certified. One run produces four governed artifacts — every property scored, every anomaly episode dated, every unresolved case queued for a human. The whole thing is versioned, unit-tested, and documented rather than a one-off script.

① Property trust summary

One row per property: the four component scores, overall trust score, trust_rating, and current_status.

② Monthly reconciliation detail

Every property-month with the three source values, pairwise diffs, alignment verdict, and suspected source.

③ Anomaly episodes

Each fast-spike / slow-drift episode with its start month, peak z-score, and duration — the queue an analyst actually works.

④ Unresolved / low-trust queue

Properties flagged ACTIVE_ISSUE or LOW_TRUST, or with an unresolved suspected source, ranked for review.

Why this one is enterprise-certified
Versioned v2 → v4 pytest suite Full data dictionary Configurable thresholds Min 12-month history gate Deterministic, re-runnable

Thresholds (tolerance, fast/slow sigma, weights) are parameters, not magic numbers; every rating boundary and status transition is covered by tests; and the full column-by-column contract lives in a committed data dictionary. See the case study for the governance history.

Try the AI-enabled catalog

A working miniature of the AI-Enabled Warehouse Catalog — the same three-tab product as the real Streamlit app, plus a view of the build pipeline. The retrieval ranking (score_table() / retrieve_tables()) and the confidence badge (confidence_score()) are ported line-for-line from app.py and run live in your browser; only the chat's answer text is pre-written (a static site can't safely make a live LLM call).

Note on data: the real project ran against an actual warehouse's query history — internal, non-public schemas and usage. None of that appears here. Every table, column, user, and number below is invented, though the shape and the heavy query-volume skew match the real catalog.

warehouse-docs · streamlit

How the catalog gets built — five stages turning raw query history into one governed, usage-ranked catalog.json. Magnitudes shown are from the real run (usage counts, not any confidential schema names).

1 · Ingest
Load 463,960 query-history rows into DuckDB; dedup on generic_query_hash.
↓
2 · Parse
Walk each query's AST with sqlglot (Redshift dialect) → column roles selected / filtered / joined + join edges.
↓
3 · Aggregate
Roll up per table: query count, distinct users, top columns by role, co-occurrence, example queries.
↓
4 · Emit catalog.json
372 tables across 53 schemas, ordered by query_count — one governed artifact.
↓
5 · LLM enrich
Claude Sonnet on the top 30 tables (SHA-256-cached) → domain labels, summaries, and FAQ cards (8 domains × 5). 0 of 61 generated citations were ungrounded.

Every catalogued table, filterable by name or domain — a plain substring filter, exactly like the app's Catalog tab (this is not the scored retrieval; that's the Ask tab). Pick a table to see its usage stats, columns by role, co-occurring tables, and an example query.

Ask a question: retrieval scores every table live, the answer is grounded only in the top hits, and a confidence badge scores the answer by how well its citations match real, high-traffic tables. Each chip lands on a different tier that actually occurs in the real app.

Live retrieval — scored across the full sample catalog

retrieval score = 3×(query ⊂ name) + 1×(word ⊂ name) + 0.5×(query ⊂ column) + log10(query_count)×0.1  ·  confidence = min(1, 0.7×grounded_ratio + 0.3×(volume_weight×10)), grounded checked against the whole catalog

The LLM-generated FAQ cards, grouped by domain — the app's landing tab. Each card cites the tables its answer rests on; every citation here resolves to a real catalogued table (grounded), mirroring the real run's 0-of-61 ungrounded result.
