Source Trust Pipeline

A governed metric that reconciles three independent revenue and rooms sources per property per month, scores how much to trust the resulting number, and flags exactly where and why the sources disagree.

Python / pandas Redshift Statistical anomaly detection Versioned pipeline (v2→v4) Unit tested

The problem

Property-level revenue and rooms figures were produced independently by three systems — Reservation, Consumed-stay, and Performance — and they didn't always agree. Nobody had a single, defensible answer to "which number is right, and how much should I trust it?" Without a governed definition, every team downstream was left to invent its own reconciliation logic, or to just pick a source and hope.

This is exactly the kind of conflicting-logic problem a governed semantic layer exists to solve: instead of three ungoverned numbers, produce one certified trust signal per property per month, with a transparent, testable, version-controlled definition behind it.

Approach

The pipeline ingests one row per property_id + stay_month with all three sources' revenue, rooms, and presence flags, and produces four governed outputs:

  • monthly_source_comparison — per-property, per-month pairwise differences, consensus values, suspected source, and rolling statistics.
  • issue_periods — consecutive alert episodes (fast spikes, slow drifts, missing sources) collapsed into month ranges rather than raw daily noise.
  • property_trust_summary / _readable — one row per property for the full report period, with an overall trust score, completeness, alignment, and current status.
Metric definition, not a one-off script. Every comparison uses one symmetric percentage-difference formula, one alignment tolerance, and one historical-baseline window — defined once, tested, and reused everywhere in the pipeline, exactly like a governed metric in a semantic layer should be.
2 × ABS(source_a − source_b) ───────────────────────────── ABS(source_a) + ABS(source_b) 0% → exact match 5% → default alignment tolerance 200% → one source is zero, the other is not

Anomaly detection: fast spikes vs. slow drift

Rather than a single static threshold, each property's current month is compared against its own trailing 12-month baseline using a z-score, so "normal disagreement" is defined per-property, not globally:

  • Fast spike — a sudden, extreme disagreement: difference > 5% and z-score ≥ 6 in a single month.
  • Slow drift — a smaller but persistent disagreement: 3 consecutive months each > 5% and z-score ≥ 2.
  • Source missing — a source stops reporting for a property/month entirely.

These episodes are what actually get written to issue_periods — collapsed into start/end months and durations, so an analyst sees "Property 4021 has had a slow revenue drift since March," not 40 rows of daily noise.

The trust score

A single weighted score per property, built from four governed components:

ComponentWeightWhat it measures
Revenue alignment35%% of evaluable months where revenue is within tolerance
Rooms alignment30%% of evaluable months where rooms are within tolerance
Completeness20%Average presence % across all three sources
Stability15%% of months with no fast-spike or slow-drift condition

The score rolls up into a plain-language trust_rating — EXCELLENT, GOOD, REVIEW, MATERIAL_CONCERN, SEVERE_CONCERN — plus a current_status field (ACTIVE_ISSUE, LOW_TRUST, HEALTHY_WITH_HISTORY, HEALTHY) so non-technical stakeholders can act on it without reading a data dictionary.

Suspected-source logic

When two sources agree and a third doesn't, the pipeline names the outlier — without overclaiming it's "wrong." If all three disagree, or fewer than two sources are available, it returns an explicit UNRESOLVED_THREE_WAY, UNRESOLVED_PAIR, or INSUFFICIENT_SOURCES classification rather than guessing.

Example: Reservation = 100, Consumed = 102, Performance = 160 → Reservation and Consumed form the within-tolerance consensus, so Performance is flagged as the suspected outlier.

Governance & change management

  • Iterated through v2 → v4 as detection rules were refined, each version keeping backward-compatible outputs and its own README + changelog-style notes.
  • A dedicated data dictionary defines every exported column, every alert rule, and every counting identity (e.g. problematic_months = alert_affected_months + outside_tolerance_only_months) so the metric is auditable without reading the code.
  • Unit tests cover the pipeline logic directly, and configurable thresholds (tolerance %, baseline window, sigma cutoffs) are exposed as parameters instead of hard-coded, so business owners can tune the definition without a code change.
  • Designed to run directly against a Redshift dataframe as the input, matching how the metric would actually be scheduled in production.

Why it matters for governed metrics

This is a working example of the exact lifecycle a semantic layer needs to enforce: a conflicting, ungoverned metric (property revenue) gets one certified definition, backed by tests, documented thresholds, and a change-managed version history — with an explicit, machine-readable confidence signal attached, instead of a silent number nobody can audit.
