AI-Enabled Warehouse Documentation Generator

Turns raw query-history logs into a governed, usage-ranked data catalog, then lets an LLM answer analyst questions grounded only in that catalog — with a visible confidence score based on how well its citations actually match real tables.

sqlglot DuckDB Claude (Anthropic API / Bedrock) Streamlit Redshift / Postgres query logs

The problem

Nobody writes documentation for a data warehouse fast enough for it to stay accurate — and the JD for this role is explicit about the stakes: generative AI applications need certified business metadata, not just raw table names, or they'll produce confidently wrong answers about metrics they were never taught to trust.

The fix implemented here isn't "write more docs by hand" — it's derive the catalog from how the warehouse is actually used, enrich it with an LLM, and then force any AI-facing Q&A to stay grounded in that same catalog instead of hallucinating.

Pipeline: five stages, one artifact

  1. Ingest — load raw query-history CSV (schema, table, user, timestamp, SQL text) from the warehouse's system tables into DuckDB.
  2. Parse SQL — run every historical query through sqlglot to extract column-level usage roles: which columns were selected, which were used to filter, and which were used to join.
  3. Aggregate — roll parsed usage up per table: query count, distinct users, top columns by role, and which tables most often co-occur in the same query.
  4. Emit catalog.json — one governed artifact per table: usage stats, top columns by role, co-occurring tables, and real example queries.
  5. LLM enrichment — Claude Sonnet assigns each table a domain label, writes a purpose/audience/use-case summary, and generates FAQ cards per domain — all cached by SHA-256 hash of the prompt so re-runs don't re-spend tokens.

Usage-ranked, not alphabetical

The catalog isn't a static schema dump — it's ordered and weighted by how the warehouse is actually queried: query count, distinct users, and table co-occurrence surface the tables analysts actually rely on, and which ones are commonly joined together. Only the top-N most-used tables are sent to the LLM for enrichment, keeping the governed catalog focused on what matters instead of documenting every unused table equally.

Grounded Q&A with a visible confidence score

The Streamlit app's chat tab doesn't just answer questions — it retrieves the most relevant tables from the catalog first (scored by name/column match and boosted by usage popularity), answers using only that context, and requires the model to cite which tables it actually used.

Those citations are then checked against the entire catalog index — every table in catalog.json, not just the handful retrieved for this question: a citation that resolves to a real catalogued table counts as grounded; one that doesn't is flagged as ungrounded. The score combines two signals so it rewards answers that are both real and well-supported:

confidence = min(1, 0.7 × grounded_ratio + 0.3 × (volume_weight × 10)) grounded_ratio = cited tables found in catalog ÷ tables cited volume_weight = query_count of cited tables ÷ query_count of whole catalog ≥ 0.8 → 🟢 High ≥ 0.5 → 🟡 Medium else → 🔴 Low

The grounding ratio is the dominant term, but the volume weight is what makes the badge honest about coverage: an answer that cites a real-but-rarely-queried table lands at Medium, while one grounded in the warehouse's most-used tables reaches High. And when the catalog simply doesn't cover a question, the system prompt tells the model to cite nothing (<cites></cites>) — which the scorer reads as Low, i.e. an explicit "not answerable from warehouse evidence" rather than a confident guess.

This is the AI-enablement pattern the role calls for: governed business context feeding an AI consumer, with an explicit trust signal attached to every answer — not a chatbot bolted on top of ungoverned tables.

Governance details

  • Supports both the direct Anthropic API and Amazon Bedrock as interchangeable LLM backends via one config flag — no code change to switch providers.
  • Every LLM call is content-hashed and disk-cached, so the enrichment step is idempotent and reproducible — re-running the pipeline doesn't silently change past documentation or burn tokens for identical input.
  • Enrichment output (domain, summary, FAQ) is written back into the same catalog.json artifact the retrieval layer reads from, so the catalog is the single governed source for both the browsing UI and the chat.
  • Parsing failures are logged rather than silently dropped, so gaps in SQL-based lineage extraction are visible and auditable.

Why it matters for a semantic layer
