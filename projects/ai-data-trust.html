AI Data Trust Platform

A microservices architecture sketch for a platform-level trust layer: sync a real data catalog, profile tables on a schedule, score and explain trust per table with an LLM, and surface it all on a dashboard with historical trend lines — the shape of a scaled-up semantic layer, not a finished product.

Alation (enterprise target) OpenMetadata (prototype) Apache Airflow Docker Compose Next.js Postgres

Honest status

This project is included deliberately as an architecture and roadmap piece, not a working demo. It's early — services are scaffolded, the orchestration is defined in docker-compose, but it hasn't been run end-to-end as a live system yet. It's here because the design decisions it captures are directly relevant to this role's "prototyping and iteration on integrated data catalog and data fabric capabilities" responsibility, even before the implementation is finished.

The idea

dap_monitor proved a trust-scoring methodology for one specific reconciliation problem (three revenue sources). This project asks: what would it look like to run that same idea — a governed, explainable trust score per table — as a standing platform service instead of a one-off script, wired into a real metadata catalog — OpenMetadata for this prototype, with the same integration targeting Alation (or DataHub) in an enterprise deployment — instead of a bespoke CSV pipeline?

Planned service architecture

  • catalog-sync — syncs table/column metadata to a metadata catalog via its REST API — OpenMetadata in this prototype, Alation (or DataHub) in an enterprise environment — so trust scores and lineage live next to the same catalog other tools already read from, instead of a second, disconnected source of truth. The catalog sits behind a thin adapter, so switching vendors is a config/adapter change rather than a rewrite.
  • profiler — scheduled Airflow DAGs that profile tables (freshness, volume, null rates, distribution drift) on a recurring cadence rather than on-demand.
  • trust-scorer — scores trust at the column level first — where completeness, alignment, and distribution drift actually live — then rolls those column scores up into a per-table score, so the weakest columns visibly drag a table down instead of being averaged away. Generalizes the weighted-component approach (completeness, alignment, stability) proven in dap_monitor beyond a single metric, and layers table-level signals (freshness, volume) on top of the column roll-up.
  • lineage-propagation — reads lineage from the catalog and lets an upstream table's low trust flow downstream: a report built on a table that just went 🔴 is flagged as at-risk even before its own profile degrades, so problems surface where they originate instead of where they're finally noticed. This is the "data fabric" angle — trust that follows the data, not just individual tables in isolation.
  • ai-expectations — uses an LLM to draft candidate data-quality expectations/rules for a table from its observed profile, then routes them to a data steward to approve, edit, or reject before they take effect — human-in-the-loop, so the AI accelerates rule-writing without silently deciding what "correct" means. Approved rules become the table's certified expectations.
  • explanations — generates plain-language explanations for why a table's trust score changed, so a score isn't just a number without a story.
  • alerting — watches the score history and notifies a table's owner when it crosses a threshold or trends down over N runs, so a decline is pushed to the people who can fix it rather than waiting to be noticed on a dashboard. Turns the platform from a passive viewer into an operational early-warning system.
  • trust-api — exposes the same scores that catalog-sync writes into the catalog for programmatic consumption at query time: an AI application (or a downstream pipeline) asks "can I trust revenue_daily right now?" and gates its own answer on the response — the machine-facing counterpart to the human browsing the catalog. This is the whole point of putting scores in the catalog: one governed source of trust, read by both people and AI.
  • dashboard — a Next.js app showing per-table trust scores with color-coded badges (🟢/🟡/🔴) and historical sparkline trends, drilling into a per-table detail view.
Orchestration: docker-compose wires up Postgres, OpenMetadata, and Airflow as the local prototype substrate, with each trust/AI service as its own container — service boundaries chosen so profiling, scoring, and explanation can evolve independently. In a Choice-Hotels-style deployment, the OpenMetadata slot is filled by the managed enterprise catalog (Alation) instead, while the trust/AI services stay the same.

What the dashboard is meant to show

The homepage renders a card per table with a score badge and a compact SVG sparkline of the score's recent history — the intent is that a governance reviewer can scan dozens of tables at a glance and immediately see which ones are trending down, not just which ones are currently red. Each card links to a per-table detail page that breaks the score back down to the column level — so a reviewer sees not just that a table is 🟡, but exactly which columns (and which signal: completeness, drift, freshness) pulled it there — alongside the full score history and drivers.

The consumption side: one trust signal, three projects

The point of scoring trust isn't the score — it's what consumes it. This platform is the scaled-up version of a pattern the other two projects already prove in miniature:

  • dap_monitor gates a reconciliation on a trust score before it's published.
  • The Warehouse Catalog attaches a confidence score to every AI answer, so an ungrounded reply is visibly Low rather than confidently wrong.
  • This platform generalizes that: the trust-api lets any AI consumer check a table's trust before it answers — the same "don't present ungoverned data as fact" discipline, now available warehouse-wide from the governed catalog.
The thesis: a semantic layer isn't finished when data is documented — it's finished when every consumer, human or AI, can tell how much to trust what it's reading, from one governed source. These three projects are the same idea at three scales.

Why include an unfinished project

Because the role isn't just "operate an existing semantic layer" — it's also "research emerging semantic layer, metadata, and AI-enablement tooling and surface findings... for evaluation," and "support prototyping and iteration on integrated data catalog and data fabric capabilities." This project is evidence of that muscle: evaluating where an off-the-shelf catalog (Alation, OpenMetadata, or DataHub) ends and where custom trust/AI logic needs to begin, and sketching the service boundaries before writing production code.
